## 1. 本地能不能做：能，但要分层看

**结论：业务侧 90% 可以在本机做完，剩下 10% 的门槛不在技术，在平台资质和风控。**

| 层 | 本地可行性 | 说明 |
|---|---|---|
| 账号库、凭证加密、代理绑定、指纹隔离 | ✅ 完全可做 | 纯本地软件工程 |
| 产品库、素材库、多语言文案、合规检查 | ✅ 完全可做 | 接本地模型网关即可 |
| 内容日历、批量排期、发布回执 | ✅ 可做 | 走官方 API 或浏览器会话 |
| 线索采集、去重、打标、轻量 CRM | ✅ 可做 | 采集走公开页 + 登录态页面 |
| 统一收件箱、AI 草稿、话术库 | ✅ 可做 | 读消息靠 API/会话，发送留人工闸门 |
| 指标快照、漏斗、内容→询盘归因 | ✅ 可做 | 需要每平台各自的拉取器 |
| 官方发布/私信 API | ⚠️ 看资质 | Meta 要 App Review + 商业验证；LinkedIn 营销 API 要公司页+申请；X 要付费档；TikTok 内容发布 API 要审核；YouTube 有配额上限 |
| 浏览器自动化发私信 / 加好友 / 批量关注 | ⚠️ 高风控 | 这是封号主因。技术上能跑，但要靠独立指纹+住宅代理+频控+灰度，且必须有熔断 |
| 平台数据大规模抓取（评论区、竞品粉丝） | ⚠️ 有边界 | 只抓公开可见面，登录态抓取风险等级更高 |

**产品设计上必须内建三件东西**，否则本地化也只是把封号搬到本机：

1. **官方 API 优先，浏览器会话兜底**：同一条发布任务先走 API，失败按错误码分类再决定降级到会话，不是无脑切。
2. **人工确认闸门**：私信、加好友、评论回复这类不可逆动作默认进审批队列（和 ARTEX 的「拦截审批」是同一个设计思路）。
3. **每账号独立运行环境**：独立浏览器 profile（UA/时区/语言/Canvas/WebGL/字体/WebRTC）、独立出口 IP、独立 cookies 库；一个号出问题不污染其它号。

## 2. 模块清单（P0 先做，P1 第二批，P2 加分）

### 2.1 账号与身份域（P0）
- 多平台账号库：平台、账号名、主页 URL、绑定的产品线、负责人、状态（正常/限流/封禁/待验证）
- 凭证加密：Windows DPAPI 包裹 AES-GCM 主密钥；DB 里只存密文 + 指纹
- 代理绑定：账号 ↔ 出口 IP 一对一，代理池健康检查（延迟、掉线、地区一致性）
- 指纹隔离：每账号一个持久化浏览器 profile，指纹参数落库，可复现
- 登录态健康检查：定时低频探测，失效告警而不是等到发帖失败
- 事件台账：登录异常、验证码、风控提示、封禁，全部留档（用于事后归因到哪类动作触发的）

### 2.2 内容生产域（P0）
- 产品/SKU 库：型号、卖点、参数、目标市场、关键词（多语言）
- 素材库：图片/视频/文档，标签、版本、EXIF/GPS 清理、去重哈希
- AI 文案工坊：英/西/阿/葡/俄/德，按平台文体（LinkedIn 长文、IG 短句+标签、TikTok 口播脚本、邮件开发信）
- 品牌语气与模板：品牌词表、禁用词、CTA 模板
- 发帖前合规检查：字数上限、hashtag 数量、敏感词、图片尺寸、链接可达性

### 2.3 排期与发布域（P0）
- 内容日历（周/月视图，按客户所在时区显示最佳时段）
- 批量排期、定时发布、跨账号同稿变体
- 发布流水线：API → 降级会话 → 失败归因（权限/限流/网络/风控）
- 回执与存档：发布 URL、帖 ID、首小时指标

### 2.4 获客域（P1，外贸核心）
- 线索采集：关键词、话题标签、群组、竞品主页、展会名单导入
- LinkedIn 画像解析：公司、职位、地区、最近动态
- 联系方式提取与校验：邮箱 MX/SMTP 探测、WhatsApp 号段校验、去重
- 线索打分：匹配度（产品/市场/职位）+ 活跃度
- 轻量 CRM：阶段（新线索→已触达→有回复→报价→成交）、跟进提醒、报价单关联

### 2.5 会话域（P1）
- 统一收件箱：FB/IG/LinkedIn/X/WhatsApp/Telegram/邮件
- 意图分类：询盘、售后、报价、垃圾
- AI 草稿 + 人工确认后发送；话术库与快捷短语
- 交接与 SLA：多久没回要提醒

### 2.6 互动与达人（P2）
- 评论区关键词监控与回复草稿
- 群组/话题参与提醒（不做自动灌水）
- KOL/达人库：粉丝量、地区、互动率、联系方式、合作记录

### 2.7 分析与复盘（P1）
- 每帖指标快照（曝光/互动/点击/私信数）
- 账号增长曲线、内容类型效果对比
- 线索漏斗、内容→询盘归因（哪条帖带来哪个线索）

### 2.8 运行支撑域（P0 骨架）
- 任务队列 + 每平台令牌桶限速 + 退避 + 冷却
- 熔断：单账号连续失败 N 次自动停用并告警
- 审计日志、备份恢复、崩溃自恢复
- 灰度发布与夜间静默（按目标市场时区）

### 2.9 AI 层（P0）
- 本地模型网关：`http://127.0.0.1:8787/v1`（本机已有）
- 分工和本机 ARTEX 编制一致：kimi 监工/审校、pro 中等分析、flash/glm 批量文案与清洗、space-bunny 长文、step-5-preview 事实校验

## 4. 技术选型建议（本地优先）

| 层 | 建议 | 理由 |
|---|---|---|
| 桌面壳 | Electron + React | 和本机 ARTEX 同栈，复用托盘/单实例/内嵌 web 的经验 |
| 后端 | 先 Go 单进程（内嵌 SQLite WAL），账号 > 200 再换内嵌 Postgres | ARTEX 已经是这个形态，能直接抄作业 |
| 浏览器自动化 | Playwright + persistent context（每账号一个 profile 目录）+ CDP | 会话可持久化、能接指纹注入 |
| 队列/限速 | 表驱动 job 队列 + 每平台令牌桶 + 指数退避 | 不引 Redis，单机够用 |
| 模型 | 本地网关 127.0.0.1:8787，OpenAI 兼容 | 已有，直接复用 |
| 凭证 | DPAPI(AES-GCM) 主密钥 + 列级密文 | Windows 本机最省事 |
| 前端状态 | TanStack Query + 本地 SSE 推送任务进度 | 发布/采集是长任务，需要实时态 |

## 5. 落地路线（按周）

- **V0（1-2 周）**：账号库 + 凭证加密 + 产品/素材库 + AI 文案 + 内容日历 + 单平台（选一个主战场）发布走官方 API + 发布回执。目标：能稳定发一条帖并看到指标。
- **V1（3-6 周）**：多账号（代理+指纹）+ 三平台发布降级链 + 统一收件箱（只读）+ 线索采集（半自动，人工确认）+ 频控熔断。
- **V2（7-12 周）**：轻量 CRM + 归因 + 评论监控 + 审批流 + 审计与备份。

## 6. 需要你定的四件事

1. **主战场平台排序**：LinkedIn 为主，还是 TikTok/IG 为主？这决定浏览器自动化投入多少——LinkedIn 的私信/加好友最敏感，TikTok 的发布接口最难过审。
2. **账号规模**：10 个以内 / 50 左右 / 200+？决定单机 Electron 够不够，还是直接上 Go+Postgres 服务端。
3. **要不要自动私信、自动加好友这类动作**：要 → 必须上独立指纹+住宅代理+审批闸门+熔断；不要 → 全走官方 API，工期省一半。
4. **部署形态**：只有你自己一台 Windows 用，还是要一台机器给团队几个人同时用？
